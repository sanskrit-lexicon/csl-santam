# Project Objective: Harden and document the csl-santam dictionary-search frontend

[csl-santam](https://github.com/sanskrit-lexicon/csl-santam) is a web-frontend port of the Cologne "MWScan tamil" multi-dictionary search ([uni-koeln MWScan/tamil](http://www.sanskrit-lexicon.uni-koeln.de/scans/MWScan/tamil/index.html)). A single search form ([php/index.html](https://github.com/sanskrit-lexicon/csl-santam/blob/master/php/index.html)) POSTs to a single endpoint ([php/recherche.php](https://github.com/sanskrit-lexicon/csl-santam/blob/master/php/recherche.php)), which queries one combined SQLite table `tamil(id, st, en)` spanning four lexica (mwd, cap, otl, cpd). Two implementations exist: the original Perl CGI (`perl/recherche.pl` + `perl/cgi-include2.pl`) and a close PHP port. Maintainer: Thomas Malten (th.malten@uni-koeln.de). Default branch: `master`. The goal of this work is to (1) close the security holes in the PHP backend and (2) replace the auto-generated README stub with substantive, factual documentation.

**Dictionaries** (id → code, per [dat/books](https://github.com/sanskrit-lexicon/csl-santam/blob/master/dat/books)):

| id | code | name | entries | status |
|----|------|------|--------:|--------|
| 1 | `mwd` | Cologne Digital Sanskrit Lexicon (Monier-Williams) | 166,434 | active (default) |
| 2 | `cap` | Capeller's Sanskrit-English Dictionary | 37,413 | active |
| 3 | `otl` | Cologne Online Tamil Lexicon | 117,773 | active |
| 4 | `cpd` | Concise Pahlavi Dictionary | 4,218 | DISABLED (option commented out in [php/index.html](https://github.com/sanskrit-lexicon/csl-santam/blob/master/php/index.html); `all` excludes via `id<4`) |

`all` = 321,620 entries = mwd + cap + otl (Pahlavi excluded; the form's hard-coded "325,838" label counts all four dictionaries).

**Data model.** `sqlite/ganz.txt` (~25 MB, tab-delimited: `dict-id<TAB>headword(st)<TAB>entry(en)`) is imported into the SQLite table `tamil(id INT, st VARCHAR(255), en TEXT)` by [sqlite/def.sql](https://github.com/sanskrit-lexicon/csl-santam/blob/master/sqlite/def.sql) and rebuilt by [sqlite/redo.bat](https://github.com/sanskrit-lexicon/csl-santam/blob/master/sqlite/redo.bat) (XAMPP `sqlite3`). The stored `st`/`en` are single-byte ASCII Harvard-Kyoto (HK) romanized transliteration (e.g. `akAra`, with `%{...}` markup), **not** Unicode script — this fact drives several "is this a bug?" judgments below.

## 🧠 Dev Notes & Hypotheses (Bugs, ideas, context)

**Data encoding is single-byte ASCII Harvard-Kyoto — this drives several "is this a bug?" judgments.** The `st`/`en` columns hold HK romanized transliteration in ASCII (e.g. `akAra`, with `%{...}` markup), **not** Unicode Devanagari/Tamil script. HK letter table: `a A i I u U R RR lR lRR e ai o au M H | k kh g gh G c ch j jh J | T Th D Dh N t th d dh n | p ph b bh m y r l v z S s h`. Two consequences that look wrong but are correct:

- **No `/u` flag in `_sqliteRegexp()` is correct here.** The regexp UDF runs `preg_match('/'.$pattern.'/i', $string)` — case-insensitive, no `/u` (UTF-8) flag. Because the corpus is single-byte ASCII, the ASCII `\b` word-boundary anchors behave as intended and `/u` would be inappropriate. This would only become a latent bug if the data were ever migrated to Unicode script. Do not "fix" it by adding `/u`.
- **`lower()` / `strtolower()` byte-wise folding is fine for ASCII** — there are no multibyte code points to mishandle. The only non-ASCII bytes live in `en` and are handled separately by the render-time `iconv("Windows-1252","UTF-8",$en)`, outside the search/matching path.

**Case-folding over case-semantic HK is a real, intentional lossiness — fix awaiting merge in [PR #14](https://github.com/sanskrit-lexicon/csl-santam/pull/14).** The search lowercases both data (`lower(col)`) and query (`strtolower`) on `master` today. But in HK **letter case is phonemic**: `A`=long ā, `T`=retroflex ṭ, `R`=vocalic ṛ, `S`/`z`/`s`=three sibilants, `N`/`G`/`J`=nasals. Folding therefore conflates genuine contrasts — e.g. `ata` and `aTa` (exact) match the **same** rows; `akAra` folds to `akara`. This is the advertised "not case sensitive" behavior of the form, so it is by design, and users cannot yet force a case-sensitive HK match on `master` — PR #14 adds an opt-out (`case_sensitive=1`) but is not merged. Do not silently change this behavior outside that reviewed PR (it alters user-facing search semantics).

**The "Pali" comment meant PAHLAVI (mislabel bug, comment-only) — fixed Wave 1.** `compute_where()`'s `all`-branch comment used to say "exclude the 4th (Pali dictionary)". Id 4 is the **Concise Pahlavi Dictionary** (`cpd`) per [dat/books](https://github.com/sanskrit-lexicon/csl-santam/blob/master/dat/books); the comment now says "Pahlavi". The behavior (`id<4`, excluding id 4 from `all`) was correct regardless.

**`sanitize_REQUEST_all()` is effectively a no-op.** It iterates every `$_REQUEST` key and runs `filter_var($old, FILTER_UNSAFE_RAW)`, writing the result back. `FILTER_UNSAFE_RAW` performs **no** filtering — it is a pass-through. (Earlier `FILTER_SANITIZE_STRING` / `FILTER_SANITIZE_URL` attempts are commented out; `FILTER_SANITIZE_STRING` is deprecated in PHP 8.2.) The actual input safety comes from the point-of-use guards added in PRs #4–#7 (escaping at output, at the SQL literal, at the `LIMIT` cast, and `preg_quote` before the regexp UDF), **not** from this function. Do not mistake this function for the defense layer when reviewing.

**Empty-query / min-length gate.** After `trim($st)` / `trim($en)`, if **neither** field has length > 1 the backend calls `fehler("No search has been formulated.")` and exits. So a single-character field is ignored; at least two characters in `st` or `en` are required. The dictionary-code lookup (`dictionary_info()`) likewise exits via `fehler(...)` on an unknown code — and that `$dictionary`-bearing message is exactly the reflected-XSS sink hardened in PR #4.

**Variable reuse trap for doc authors.** The result loop rebinds request-scoped `$st`/`$en`/`$id` via `list($id,$st,$en) = $result;`, shadowing the top-level request variables of the same name. Harmless but a readability hazard when tracing data flow.

**Final SQL shape** (for reference):
```sql
SELECT id, st, en FROM tamil
WHERE <dict-cond> [AND <st-conds…>] [AND <en-conds…>]
ORDER BY st COLLATE NOCASE LIMIT <(int)maxhits>;
```
`<dict-cond>` = `id=N` (single dict, `dictnum>0`) or `id<4` (`all`, where `dictnum=0`). Match modes built in `where1()`: `exact`→`\bTERM\b`, `prefix`→`\bTERM`, `suffix`→`TERM\b` via the `regexp` UDF (registered in `selectfromdb()` as `sqliteCreateFunction('regexp','_sqliteRegexp',2)` over a PDO `sqlite:` connection); `substring`→`LIKE '%TERM%'` native. Per field the value is split on `preg_split('/ +/', …)`; multiple words per field and both fields filled are **AND**-joined; there is no OR and no phrase search anywhere in the query builder.

**Perl/PHP parity.** The PHP port is a close port of `perl/recherche.pl` + `perl/cgi-include2.pl`. The one documented divergence: PHP dropped the Perl `maxhits` "all" option (`<option value=1000000>all` is HTML-commented in [php/index.html](https://github.com/sanskrit-lexicon/csl-santam/blob/master/php/index.html)); PHP choices are `20/50/100/200/500/1000` (default 50). Both share the same data path (`ganz.txt` → `def.sql` → `tamil.sqlite`). Perl does the Windows-1252→UTF-8 conversion itself; PHP does it inline per row.
